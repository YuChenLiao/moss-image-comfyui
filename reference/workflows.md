# 工作流与运维

## 四种工作流

| 场景 | 链路要点 |
|---|---|
| 文生图 | `EmptyFlux2LatentImage` → KSampler(denoise 1.0) |
| 图生图 | `LoadImage` → `ImageScaleToTotalPixels(megapixels=2.3, resolution_steps=16)` → `VAEEncode` → KSampler(denoise 0.9) |
| 局部重绘 | 蒙版取红通道 → `GrowMask(expand=12)` → `SetLatentNoiseMask` → KSampler(denoise 1.0) → `ImageCompositeMasked` 按蒙版贴回原图 |
| 高分辨率 | 直接给 2MP 尺寸，不要低分放大（MOSS 的 i2i 会重绘，放大不增细节） |

**`ImageScaleToTotalPixels` 的 megapixels 决定输出画布**，默认 1.0 会把输出压到 1MP。参考图再大也没用，这一项不调高，出来就是 832×1264 这种尺寸。

局部重绘的合成步骤很关键：蒙版外像素可做到字节级不变（实测 99.49% 像素零变化），因为非编辑区是贴回原图而不是重新生成。

蒙版图白色 = 重绘区，尺寸可与原图不同（用 `GetImageSize` + `ImageScale` 动态对齐）。

## 画幅决定手会不会崩

i2i 的输出画幅**跟随参考图**（`ImageScaleToTotalPixels` 按原图比例缩放）。参考图是 9:16 长条时，人物被撑满画面、手腕与脚踝顶到画框，被裁掉的那部分必然画崩。

实测（844×1500 参考图、denoise 0.92、24 步、同一套词）：

| 画幅 | 输出尺寸 | 结果 |
|---|---|---|
| 9:16 原比例 | 1168×2064 | 手在画面上缘被裁，手指糊成一团；构图到腰臀就出框 |
| **3:4 加宽** | 1344×1792 | 双手完整入画、五指分明；膝盖与臀部都有边距 |

做法：

1. 把参考图垫进一块更宽的画布（3:4 或 1:1；1120×1500 其实已是 3:4，别写成 4:5），原图居中，四周补背景色（黑床单就补黑、边缘做一点羽化），另存成新文件喂 `image`；
2. 提示词写死构图：`人物占画面约七成，头顶、手腕、两膝与臀部都留有边距，没有任何部位被裁切`；
3. 负面压 `hands out of frame, cropped hands, cropped knees, legs out of frame`；
4. **不要靠提高 megapixels 解决**——加宽靠的是比例与留白，不是像素。面积只是把显存余量压薄，崩图另有诱因（见「性能」节的排查清单）。

反过来也有代价：画幅越宽人物越小，手部像素变少、畸形率反而上升。要"全身 + 手细"就得拆成两张——一张半身（留白足够，手是重点），一张全身（构图完整，手小）。同一张里两头都要，通常两头都不到位。

## 崩图排查：面积只是其中一项

分辨率没有硬上限。2016×1152 很稳，1344×1792（2.41MP）在这台机器上连续跑了十几张也没事；反过来，2688×1536（4.13MP）那次确实把进程干掉了——但那次的背景是 bf16 权重占 18.6GB、加上同进程里切过档。**同样的尺寸换到干净显存 + int8 权重，未必会崩。** 所以别把锅全扣在像素上，按顺序看：

| 顺序 | 查什么 | 怎么判 |
|---|---|---|
| 1 | 崩在哪个阶段 | 日志掉在采样 → 显存/注意力；掉在 VAEDecode → 解码峰值；跑完变慢 → 碎片 |
| 2 | 显存余量 | `/system_stats` 的 `vram_free`，干净时约 19.4GB；只剩零点几 GB 就是碎片态，重启 |
| 3 | 权重精度 | bf16 约 18.6GB vs int8_convrot 约 12GB；同进程来回换档必然变慢甚至更慢于 bf16 |
| 4 | 注意力与节点版本 | sparse / blockcache 之类插件的实现与版本，换版本后先用小图验证 |
| 5 | 文本长度 | 超长 prompt 抬高编码器显存与耗时，先砍重复措辞 |
| 6 | 并发进程 | 同时跑图、开着大页面的浏览器都会抢显存 |
| 7 | VAE 与大图 | 大画幅的解码峰值常高于采样峰值，可换 tiled decode |
| 8 | 驱动与系统 | ROCm 版本、32GB 内存下的 swap，都会表现为"随机崩" |

`scripts/frame.py --factors` 会把这张表打出来。它只报"落在什么区间"，不判对错——面积大不是错误，只是余量薄了。

## 性能

- 冷启动第一张含模型加载，比热缓存慢 1.5~3 倍。
- 连续出图 6~8 张后显存碎片累积，耗时会从 70s 涨到 700s；重启 ComfyUI 后显存从 12.4GB 回落到 4.4GB，速度恢复。
- 20GB 显存下 bf16 DiT + int8 文本编码器 = 19GB，每张图都要重新 staged 一遍，这是慢的主因，换量化权重能根治。
- 实测耗时参考：2.3MP / 60 步约 225~240s；1MP / 50 步约 70s（量化）；1MP / 20 步约 35s。

### 700s 的第二个诱因：同进程内切换权重（2026-10 实测补充）

上一版把"700s"只归因于连续出图的显存碎片，不完整。同一进程里**从 bf16 切到量化版后的第一张**同样会飙：

| 场景 | 参数 | 耗时 |
|---|---|---|
| bf16 首张（18.6GB 占用） | 2.4MP / 50 步 | 706s |
| 紧跟其后、同进程内的量化版 | 2.4MP / 50 步 | **826s** |
| 显存干净时的量化版 | 2.4MP / 50 步 | **205s** |

826s 比 bf16 还慢，原因不是量化无效，而是前一个任务卸载 18.6GB 后显存没有清干净，量化版的 12GB 权重还要重新 staged 一遍。判别方法：队列为空、但 `/system_stats` 里 `vram_free` 只剩零点几 GB，就是碎片态；真正干净时 20GB 卡应显示空闲约 19.4GB。

**结论：不要在同一进程里来回切 bf16 与量化权重。** 二选一用到底；要换档就重启 ComfyUI 再跑。205s 才是这台机器 2.4MP / 50 步的真值。

### 测速前必须换 seed（否则读数是假的）

ComfyUI 有**节点级执行缓存**：提示词、seed、输入图与全部参数一致时，它直接复用上次的结果，几秒就返回，产物连编号都沿用上次的。实测遇到过"5 秒完成"。

判断方法：产物字节数与上次完全一致、文件名编号相同，就是缓存命中。要测真速度，改 seed 或改任一参数让缓存失效。

### megapixels 会略超设定值

`ImageScaleToTotalPixels` 的 `megapixels` 是**目标面积**，宽高各自向上对齐到 16 的倍数之后会溢出。实测 1200×844 的参考图设 `megapixels=2.3`，输出 1856×1296 = **2.41MP**，比设定值高约 5%。2.3 是舒适区而非上限，但别以为拿到的就是 2.3MP。

## 8 步 DMD 加速

上游仓库 `lodestones/MOSS-Image-SFT-8-steps-dmd`（apache-2.0，从 MOSS-Image-SFT 的 50 步 CFG 3 蒸馏）。它把 8 次网络评估替代 50 步采样，理论上是"8 步、无 CFG"。

**装法**：下载 `lora.safetensors`（1.13GB，252 组 kohya 键）到 `models/loras/`，用 `LoraLoaderModelOnly` 接在 `UNETLoader` 之后。仓库里另有 `lora_latest.safetensors`，作者建议 0.7 强度。

```
UNETLoader → LoraLoaderModelOnly(1.0) → KSampler
```

**必须去掉 SLG**。`SkipLayerGuidanceDiTSimple` 每步要跑两次前向，8 步变 16 次，加速直接归零。

### 图生图也要接 LoRA

i2i 的加速链路把 LoRA 插在 VAEEncode 之后、KSampler 之前：

```
LoadImage → ImageScaleToTotalPixels(megapixels=2.3) → VAEEncode
  → LoraLoaderModelOnly(1.0) → KSampler(denoise 0.9, steps 12, cfg 1.5)
```

实测 1264×1904 约 58s。**同耗时下 i2i 的姿态比 t2i 更贴参考图**，因为 denoise 0.9 保留了参考图的构图轮廓，空间结构不会跑偏。但 denoise 意味着九成内容仍是重绘，精确的关节落点依旧不如 50 步。

| 配置 | 耗时 | 复杂姿态（一手撑地一手搭膝）的还原 |
|---|---|---|
| t2i 12 步 + LoRA | 58.8s | 右手抬到肩旁，退化 |
| i2i 12 步 + LoRA | 58.3s | 右手落在身侧裙边，接近 |
| t2i 50 步 | 190.6s | 右手正确搭在膝外侧 |

**复杂动作的推荐流程**：i2i + 12 步确认构图与姿态方向（一分钟内），要补关节精度再提到 **16–24 步**（仅 L3 需要，见下节「步数分档」）。

### 实测参数（1264×1824，同一提示词与 seed）

| 配置 | 耗时 | 相对 50 步 | 画质 |
|---|---|---|---|
| 50 步 CFG 3.5（原版，无 LoRA） | ~230s | 1× | 基准 |
| 8 步 CFG 1.0 | 30.2s | 7.6× | 连裤袜出现圆形破洞伪影，怀表退化成比手势 |
| 8 步 CFG 1.5 | 36.2s | 6.4× | 良，怀表正常、无破洞 |
| 8 步 CFG 2.0 | 36.3s | 6.4× | 良，手部略变形 |
| 12 步 CFG 1.5 | 50.1s | 4.6× | 最好，细节最干净 |
| 16 步 CFG 1.5 | 63.4s | 3.6× | 更细，收益递减 |

### 步数分档：12 步常规，16–24 步给 L3，不要上 50 步

DMD 的步数跟着需求走，不是"越高越好"：

| 档位 | 适用 | 耗时（1312×1840 i2i） | 表现 |
|---|---|---|---|
| 8 步 | 试构图、换 seed 找方向 | ~36s | 构图可用，细节粗，道具容易糊 |
| **12 步（默认）** | 常规出图、光影要求不强（平光、纯色/简单背景、单角色单道具） | ~58s | 细节干净，光影偏平 |
| 16 步 | 折中 | ~73s | 结构在，光比弱一档 |
| **24 步（L3）** | 强光影、复杂结构刻画（胯部/手部/褶皱/材质）、多道具多人 | ~106s | 光影层次与解剖结构都立得住 |

**50 步不要用。** DMD 是蒸馏档，目标就是十几步；拉到 50 步等于让一个只会十几步的模型硬走完 50 步，后半段结构会散：部件丢失（袜子、裙摆凭空消失）、发丝与光环变成涂鸦式笔触、肢体比例被拉长。

同提示词、同图生图参数（denoise 0.9、1312×1840、50 步档 CFG 3.2 那组词）实测对比：

| 配置 | 耗时 | 结果 |
|---|---|---|
| DMD 开、16 步 CFG 1.5 | 72.7s | 部件全在，光影偏平、投影很淡 |
| DMD 开、24 步 CFG 1.5 | **105.6s** | 结构完整，光影与胯部同样到位，部件没丢 |
| DMD 关、50 步 CFG 3.2 | 207–212s | 光影与胯部到位，但袜子/裙摆两版各丢一次，光环始终是涂鸦 |

分工：**8 步试构图 → 12 步常规出图 → 16/24 步只在 L3 定稿**；只有"必须在 CFG 3 上让负面生效"（压参考图串色、压兽耳尾巴）时才关 LoRA 走 50 步，那是为了 CFG 不是为了步数。

### 与上游说法相反的一条

README 写的是"8 步、no CFG"，实测 **CFG 1.0 会出伪影**——连裤袜长出一片圆形破洞、手里的怀表退化成手势。调到 1.5 立刻恢复正常。原因是这个蒸馏还不彻底，需要一点 CFG 把语义拉回来。CFG 低于 2 时负面提示词基本不起作用，负面里写的约束在这个档位要靠正向描述补。

**取舍**：DMD 档的语义遵循度低于 50 步档，细碎道具容易丢（实测两只手的手套被画成白色方块）。**常规图 12 步就够**；只有多道具、多角色、强光影与结构刻画的 L3 场景才提到 16–24 步。

**推荐**：试构图 8 步 CFG 1.5（36 秒一版）；常规出图 **12 步 CFG 1.5**（约 58s）；光影/结构要求高的 L3 用 **24 步 CFG 1.5**（约 106s@1312×1840）。**不要为了"更精细"把 DMD 拉到 50 步**——蒸馏档过采样会散结构，详见上文「步数分档」。

## 常见故障对照

| 症状 | 原因 |
|---|---|
| 输出纯彩色噪声 | 套了 `ModelSamplingSD3`；或 i2i 的 denoise < 0.85 |
| 五官糊、细节少 | 分辨率不足（<1.5MP）或人物占比太小 |
| 角色特征错（发色/瞳色不对） | 用了中文角色名或错误 tag；或中文段里重复写了外貌词把 tag 顶掉——先删外貌描述，再查 Danbooru 官方标签（见 `prompting.md`「有角色 tag 就不补外貌」） |
| 画面突然变水墨/厚涂 | 缺 `anime style, cel shading`；或换了 `@wlop` 这类半写实画师 |
| 生成到一半 ComfyUI 进程消失 | 显存压力，但通常是多因素叠加：面积 × 权重精度 × 碎片 × 同进程切档 × 注意力实现。先看日志掉在采样还是 VAE 解码阶段 |
| 提示词元素缺失 | 顺序错乱（中文描述混进了 character/series 段之间）；按官方顺序重排 |
| 皮肤像涂了油、塑料感、高光过曝 | 正向里有 `wet, sweat, water drops, 汗珠, 湿润` —— 这些词会把皮肤推成镜面反射，叠加 4 步 turbo 的粗糙采样就是塑料感。删掉它们并写进负面 `oily skin, plastic skin, glossy, harsh highlight`，换成「柔和的漫射光、高光只落在受光凸起处」 |
| 画师风格出不来 | 先删掉画师 tag 上的权重（`(@artist:1.3)` → `@artist`），权重反而会把画面推离该画师的调子；其次是底模与步数，8 步 DMD/turbo 档会削弱画师特征，提到 24 步或换 SFT 档 |
| DMD 档出图越算越崩（部件消失、发丝涂鸦、腿被拉长） | 步数超过了蒸馏目标。常规 12 步、L3 才 16–24 步，不要上 50 步（见「步数分档」） |

## 参考图 + 姿势参考（双图输入）

要「人设图定角色、姿势图定姿势」时，**只有一条路走得通**：参考图走 i2i 当首帧 latent，姿势图走 `MOSSImageControl` 的 depth map。

| 环节 | 节点与参数 |
|---|---|
| 参考图 | `LoadImage → ImageScaleToTotalPixels(megapixels=1.0) → VAEEncode → KSampler.latent_image`，denoise 0.85~0.87 |
| 姿势图 | `LoadImage → DepthAnythingV2Preprocessor(vits) → ImageScaleToTotalPixels → MOSSImageControl(depth_map, strength 0.7, end_percent 0.7)` |
| 控制权重 | `LoraLoaderModelOnly(moss_image_color_depth_control.safetensors, 1.0)`，接在 UNETLoader 之后 |

**不要用 `ReferenceLatent` 承载参考图。** 它是给 Qwen-Edit / Flux Kontext 那类编辑模型设计的，MOSS 上会把参考图当结构图处理：双参考图串起来出糊图，单参考图直接把画面画成铅笔素描。`model_base` 里虽然有 `reference_latents` 的实现，但那不是给这条链路用的。

两张图的分工有主次：参考图是首帧，**决定了画布比例、大致构图、角色底子**；姿势图只约束姿态和前后关系。两者冲突时参考图赢——拿站姿立绘配跪姿参考，出来的还是竖长画布、构图偏立绘，只是人物跪下来了。想要姿势主导，就换一张姿态接近的人设图，或者把 denoise 提到 0.9。

深度模型必须放在插件自己的目录：`custom_nodes/comfyui_controlnet_aux/ckpts/depth-anything/Depth-Anything-V2-Small/`。放 `models/controlnet/` 不会被识别，节点会去 HF 重新下载并卡在下载状态。

## 配套节点

`MOSSPromptComposer`（MOSS 提示词编排器，`custom_nodes/moss_prompt_composer/`）：角色 3098 项（2138 中文名 + 960 Danbooru 英文补充）、画师 5000 项，按官方顺序自动重排传入的提示词，输出 `positive` / `breakdown`。选角色显示中文名、写入标签；`artist_custom` 可填列表外的画师。

`MOSSCharacterPrompt`（MOSS 角色提示词）：更轻量的角色/动作选择器，输出纯提示词字符串。
